GUIDE INDEX / OPERATIONS

Reference material for
real work.

Use these starting points to structure an investigation or review. Always validate against your own platform, policies and change process.

01 / CHANGE CONTROLCHECKLIST

Before you change a production system

Capture the current state, map dependencies, agree the maintenance window, prepare a rollback and define how you will verify success.

  • Record current configuration and health
  • Confirm owners, impact and dependencies
  • Prepare and validate rollback steps
  • Set a post-change verification window
02 / BACKUP & RECOVERYREVIEW

What to check in a backup assessment

Move beyond green job status. Check coverage, retention, immutability where required, workload consistency and the practical path to restore.

  • Identify critical systems and recovery targets
  • Check exclusions and application-aware settings
  • Review job failures, capacity and retention
  • Plan a restore test and record evidence
03 / HYPER-VOPERATIONS

Building a useful virtualisation inventory

Inventory should help answer operational questions: what runs where, what it depends on, how it is protected and where capacity is tightening.

  • VM, host, cluster and storage relationships
  • CPU, memory and disk trends over time
  • Checkpoint, integration and backup status
  • Lifecycle risks and unknowns
04 / IDENTITYBASELINE

Reviewing identity and access

Understand how users authenticate, where privilege is assigned and whether access practices match the organisation's risk and support model.

  • Privileged roles and account ownership
  • MFA and sign-in controls
  • Joiner, mover and leaver processes
  • Break-glass access and review cadence
05 / NETWORKINGDIAGNOSIS

A structured approach to connectivity issues

Test the path in layers before changing configuration. Separate name resolution, routing, filtering, listening services and application behaviour.

  • Confirm source, destination and expected port
  • Check DNS and route selection
  • Validate listeners and firewall policy
  • Capture evidence before remediation
06 / DOCUMENTATIONHANDOVER

What a useful runbook should contain

A runbook should help another engineer safely repeat a task, recognise failure and know when to stop and escalate.

  • Purpose, prerequisites and scope
  • Numbered steps with expected results
  • Failure paths and escalation points
  • Validation, rollback and ownership

These notes are general guidance, not a substitute for vendor documentation, environment-specific testing or an approved change process.
